# 认识 Agent Harness

[序章](00_index.md#一句话请求先要落到正确的工作区)沿一次配置修复走到了交付判断；本章从这条链路反推它所依赖的系统。请求仍然是“修复这个仓库里的配置解析错误，运行相关测试，并解释修改”。如果把它交给一个只会对话的模型，模型可以分析报错，也可以建议怎样改代码；但它并不知道当前工作目录是不是目标仓库，不会自动读取项目约定，也没有天然的文件写入、命令执行或 Git 权限。即使模型给出了正确补丁，谁来把补丁写入磁盘、运行测试、收集退出状态，并在测试失败后把结果送回模型，仍然是没有回答的问题。

Agent Harness 正是连接这些环节的工程系统。它把一句自然语言目标放进真实工作区，为模型准备当前所需的代码和指令，把模型提出的行动变成文件读取、编辑、命令或其他结构化工具调用（Tool Call），再把执行结果带回下一轮判断。与此同时，它还要管理权限、会话、上下文长度、中断恢复以及最终交付的代码差异（diff）和测试结果。模型决定“下一步可能做什么”，Harness 决定“这一步如何在一个有边界、可观察的环境中发生”。

本报告研究 Aider、Codex、DeepSeek Harness、Gemini CLI、Goose、OpenCode 与 Pi。它们都面向 Coding 场景，却选择了不同的控制中心：有的围绕编辑与 Git 组织任务，有的围绕会话和事件运行，有的把能力装配成插件组合，还有的刻意保持一个很小的核心，把更多选择交给扩展和宿主环境。这里的“宿主”是承载并运行 Harness 核心的应用、进程或运行环境，它可以负责注入模型路由、工具、权限与存储。理解这些差异，比数一数界面上有多少按钮更接近 Harness 的本质。

## 从一次修复任务看 Harness

配置解析错误看似简单，真正执行时却会迅速展开。系统首先要确认仓库和工作区，读取项目说明，找到报错对应的配置入口与测试；随后，模型可能请求搜索文件、查看实现、修改代码并运行测试。每个动作都会带回新的信息：文件不存在会推翻原来的猜测，测试失败会暴露遗漏分支，Git diff 会显示模型是否改动了目标之外的内容。任务因此不是一次“提示词输入—补丁输出”，而是一个不断由现实反馈修正判断的循环。

推理与行动（Reasoning and Acting，ReAct）用两者交替说明了这种反馈为何重要：行动从外部环境取得新观察，新的观察再影响后续决定 [@yao2023react]。在软件工程中，SWE-agent 将仓库导航、文件编辑和测试执行等接口概括为智能体—计算机接口（Agent–Computer Interface，ACI），并展示了接口设计本身会显著影响 Agent 的行为 [@yang2024sweagent]。对于 Coding Agent，模型能力固然重要，但模型看见什么工具、工具返回什么信息、失败怎样继续，往往同样决定任务能否完成。

可以把一个典型 Harness 循环理解为下面几步：

```text
准备本轮可见的指令、代码与工具
→ 请求模型提出回答或行动
→ 检查行动是否符合参数和权限要求
→ 在工作区执行行动
→ 把结果、错误或拒绝原因送回下一轮
→ 达到完成条件，或把控制交还给用户
```

这段流程只是帮助建立直觉，并不意味着七个系统共享同一套内部状态机。Aider 可以从模型生成的编辑格式（edit format）进入修改流程；这是一种受约束的文本编辑表示，由 Harness 解析后应用到文件。Codex、Gemini CLI、OpenCode 与 Pi 更多使用前文所说的结构化工具调用，Goose 的能力大量来自扩展，DeepSeek Harness 则由插件组合决定一次 Agent 实际拥有的能力。编辑格式与 Tool Call 都能承载行动提议，但它们对参数校验、错误反馈和可保存状态的组织方式不同。七个系统都完成“行动—观察”的闭环，动作如何表达、由谁调度以及什么状态能够保存，却有很大差异。

Harness 也不是模型外面的一层薄包装。它至少同时承担四类工作。第一类是理解环境：发现工作区、读取项目指令并选择模型本次真正需要的本轮上下文（Context）。第二类是组织行动：持续推进对话或任务，把模型请求路由到文件、命令行（Shell）、Git、模型上下文协议（Model Context Protocol，MCP）服务或其他工具。第三类是控制副作用：处理确认、权限与隔离，决定某个动作能否真的改变文件、进程或网络。第四类是维持连续性：保存会话，在上下文过长时压缩历史，并在中断后恢复足够状态继续工作。不同产品对这四类工作的拆分，构成了后文比较的主线。

这里需要分清模型、Agent 与 Harness。模型根据输入生成内容或行动建议；Agent 围绕一个目标持续选择下一步；Harness 则提供 Agent 能够看到、调用、改变和保存的工程环境。三者可以由同一个应用封装在一起，但分析时分开更有用：更换模型未必改变权限系统，增加工具也未必改善任务规划，而恢复一段会话更不等于恢复已经结束的外部进程。

判断 Harness 与相邻系统的边界，关键不是产品名称，而是谁拥有从目标、行动到环境反馈的持续运行闭环。智能体框架（Agent framework）主要提供构建 Agent 的库和组合原语，模型上下文协议服务器（MCP server）主要通过协议提供工具或数据，本身通常不负责推进完整任务；集成开发环境智能体（IDE agent）描述的是用户入口，它可以内嵌 Harness，也可以只是连接远端 Harness 的客户端。云端控制平面（control plane）更侧重租户、身份、策略与远端执行资源，只有在直接持有任务循环和会话状态时才进入 Harness 边界；基准测试编排器（benchmark harness）则从外部批量提交、记录和评分任务，被测 Agent 的执行运行时才是本报告关注的 Harness。一个产品可以同时跨越几类，判定时应看实际责任而不是标签：有界面的产品不一定拥有任务循环，提供工具的服务器也不一定拥有会话，而同一产品完全可能同时跨越客户端、Harness 与控制平面。

## 七个系统提供的不同观察窗口

把七个系统放在一起，可以看到同一类 Coding 任务至少存在四种不同的组织方式，也能从不同角度观察 Harness 如何连接模型与真实工作区。[横向能力地图](02_horizontal_capability_map.md#四种控制中心)会把它们归纳为编辑事务、会话运行时、插件装配和可编程小内核四种控制中心；这里先说明每个样本为何提供不同的观察窗口，而不把四类当作产品排名或互斥标签。

Aider 最容易从“结对编辑器”来理解。它把对话、仓库地图、编辑格式、自动代码检查（lint）和 Git 工作流紧密连接起来，适合观察专注代码修改的闭环怎样形成。Codex 更像一个通用的本地 Agent 运行时：会话（Session）、轮次、工具事件、审批和沙箱共同组织一次任务，交互与非交互入口可以复用相当一部分核心能力；固定版本还实现了可配置的内建多 Agent 路径，但只有在 `multi_agent_v2` 被启用并向当前会话暴露时，子任务工具才可用。

DeepSeek Harness 提供了另一种视角。它的核心循环相对小，模型路由、工具、持久化、权限、压缩和委派能力更多由宿主与智能体预设（Agent preset）组合出来；预设是按作用域装入的一组提示、工具和行为配置，因此特别适合观察“产品行为如何由插件装配而成”。Gemini CLI 则把终端产品与可复用核心分开，并用客户端循环和工具调度器连接模型、确认策略与执行结果，呈现出较清晰的编排层次。

Goose 将模型服务适配层（Provider）、MCP 扩展、权限和持久会话放在平台中心，同时服务命令行、桌面和接口场景。OpenCode 也强调会话、模型适配、工具与权限的可组合性，并存在当前产品链与新核心逐步衔接的演进状态。Pi 走向另一端：默认 Coding Agent 只有少量基础工具，但提供可嵌入的 Agent、树形会话和 TypeScript 扩展，把许多治理与高级能力留给扩展或宿主。

本报告研究这七个固定版本，聚焦 Coding 场景中的代码与文本上下文、工具调用、文件和进程副作用、会话、记忆、压缩、委派与安全控制。比较的目的是理解设计取舍，而不是给产品排名；图片、截图和附件等多模态能力不在本报告范围内。工程描述以固定版本的实际实现为依据，论文用于解释背后的原理。

## 用四章建立整体认识

第一部分按“先有直觉，再看差异，然后沿时间和结构深入”的顺序展开。本章先回答 Agent Harness 是什么，以及为什么模型之外还需要这样一个工程系统。[横向能力地图](02_horizontal_capability_map.md)把七个系统放进同一张静态地图，比较循环、上下文、工具、扩展、会话、令牌成本、子 Agent 和安全控制分别位于哪里。

[纵向生命周期](03_vertical_lifecycle_walkthrough.md)沿开头的配置修复任务向前推进。它不再问“系统拥有什么”，而是观察工作区绑定、上下文准备、工具执行、测试反馈、压缩、委派与恢复在什么时候发生。这样，能力表中的一个短词会重新变成有顺序、有失败分支的工程过程。

[统一参考架构](04_reference_architecture.md)再把前两种视角合并成一套最小结构，严格定义会话、轮次、消息、事件、工作单元、本轮上下文、可检索记忆与任务产物等对象。它不是要求七个项目使用相同术语，而是提供一层翻译，让读者能够分清“历史保存了什么”“本次模型看见什么”“系统允许做什么”以及“外部世界已经改变了什么”。

这四章分别提供概念、地图、时间线和结构图。第一次接触 Harness 的读者可以在本章之后先读纵向生命周期与统一参考架构，把横向能力地图留作后续查询；已经熟悉 Coding Agent 的工程读者则可以直接从横向地图进入，在遇到时间关系或术语歧义时再转到纵向生命周期和参考架构。

## 本章小结

Agent Harness 把模型的生成能力接入真实软件工程环境。它准备上下文，组织行动与反馈，控制文件、进程和网络副作用，并维持一项任务跨轮次甚至跨进程的连续性。七个样本共享这些基本问题，却以编辑事务、Session 运行时、工具调度、插件装配和可编程小内核等不同方式回答它们。

接下来不急于追踪一次任务的全部细节，而是先把七个系统摆在同一张静态地图上。第二章将回答：当用户看到相似的 Coding Agent 体验时，真正隐藏在背后的能力边界和控制位置有哪些不同。

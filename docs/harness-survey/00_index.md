# Agent Harness：架构、工程与安全

设想你把一句看似普通的要求交给编程智能体（Coding Agent）：“请在这个已有仓库中定位并修复配置解析错误，运行相关测试，并解释修改。”理想的结果很清楚：错误被找到，补丁只改变必要部分，测试给出可信结果，最后的说明能让人判断修改是否值得接受。然而，从这句话到那个结果之间，并不存在一条由语言模型独自铺成的直路。

模型可以解释报错、阅读代码片段，也可以提出修改方案；它本身却不知道“这个仓库”究竟是哪一个目录，不会天然遵守项目约定，更不能只凭一段生成文字就证明某个文件已经改变、某条测试已经执行。把语言能力接到真实软件工程环境上，并让每一步可以继续、受控和检查，正是 Agent Harness 要解决的问题。本序章沿这次配置修复逐步展开这层工程系统，再给出阅读整份报告所需的三种视角和几条路线。

## 一句话请求，先要落到正确的工作区

任务开始时，最先出现的往往不是代码问题，而是位置问题。Harness 需要确认工作区（Workspace）：当前目录是否真是目标仓库，仓库处于哪个分支，已有未提交修改是否属于用户，测试和依赖应当在哪个环境中运行。若这一步错了，模型之后再精确的分析也可能作用于错误副本，甚至覆盖不相关的工作。

位置确定之后，系统还要准备项目指令和本轮上下文（Context），也就是模型这一次实际看见的材料。用户目标、项目规则、当前环境、相关代码、已有报错、工具说明和最近结果都可能进入 Context，但整个仓库与全部历史通常不可能原样塞进去。Harness 必须选择先给什么、暂时省略什么，并保留不同材料的来源。用户要求表达意图，项目规则给出局部约束，命令输出描述某一时刻的现场，而模型先前的总结只是可能被新事实推翻的解释。

同一个仓库也不会始终提供同一幅现场。用户可能已经改过一半配置，依赖安装状态可能与文档预期不同，环境变量还可能覆盖文件里的值。Harness 若只把一小段代码交给模型，就会丢失真正决定错误是否出现的运行条件；若不加选择地交出所有环境信息，又会引入噪声和不必要的敏感内容。准备 Context 因而同时是相关性、时效性与边界管理的问题。

于是，第一轮有效工作通常不是立刻写补丁，而是缩小问题：确认错误能否复现，找到配置从哪里进入系统，判断失败发生在读取、覆盖还是校验阶段，并找到邻近测试。这解释了为什么 Coding Agent 不是“把仓库作为一个超长提示词发给模型”。Harness 需要在模型每次调用之前重建一份够用、不过载、仍能追溯来源的工作视图。[认识 Agent Harness](01_introducing_agent_harness.md)会进一步区分模型、Agent 与 Harness，并说明七个系统为何都是观察这类问题的窗口。

## 一个建议怎样变成现实中的行动

掌握第一批线索后，模型也许建议搜索某个配置项、读取解析路径、编辑一个条件分支，再运行针对性测试。这些仍然只是行动提议。Harness 要把提议变成参数明确的读取、编辑或命令调用，判断动作是否需要用户同意，再交给执行环境。权限判断表达“这次行动是否获准”，沙箱、容器或操作系统限制则约束行动获准后实际能够影响的范围。

动作执行后，现实会给出环境观察（Observation）：搜索可能没有命中，编辑可能因文件已变化而无法应用，测试可能暴露另一个兼容分支，也可能因为命令或依赖错误根本没有触达待测逻辑。Harness 要把输出、错误、退出状态和被截断的信息归回相应行动，再放进下一轮 Context。模型据此修正判断，提出下一步；Harness 再次检查、执行并收集结果。这个反复推进的运行循环（Harness Loop），才让“定位并修复”从一次猜测变成受现实反馈约束的过程。

这里也能看到安全为何不是任务结束前额外加上的一道检查。仓库内容、历史输出和外部工具都可能影响模型的建议，而读取、写入、启动进程、访问网络带来的后果并不相同。系统必须在最终参数已经明确时判断行动，把拒绝、取消和执行失败当成可继续处理的结果，并让用户在需要时取得控制权。一个界面上出现过“允许”，不等于外部副作用从此都安全；一个模型声称“已经修改”，也不等于磁盘上的结果确实如此。

循环是否可靠，还取决于观察能否与行动准确对应。若系统同时读取多个位置或并行运行检查，返回顺序可能与发起顺序不同；若输出过长，末尾的退出原因也可能没有进入模型视野。Harness 需要保留足够的关联和完成信息，避免把一个动作的成功安到另一个动作上，也避免把“尚未收到结果”误写成失败或完成。这些看似琐碎的运行细节，最终会直接改变模型对代码的判断。

如果只看某一时刻，循环像是“模型调用工具”；沿时间看，它其实是一条由目标、行动、授权、执行、反馈和终止判断组成的链。测试失败会把任务送回调查，权限拒绝可能要求改用只读方案，用户补充条件会改变后续方向。[一次任务的纵向生命周期](03_vertical_lifecycle_walkthrough.md)会把这些分支、错误与控制权变化正式展开；序章只需要先建立一个直觉：模型产生下一步的候选，Harness 负责让下一步在有边界的现实中发生。

## 当任务装不下、做不完或被打断

配置错误有时牵涉多个包。随着搜索结果、失败日志、修改尝试和测试输出不断累积，令牌（Token）预算会逼近模型的上下文上限。此时，继续把所有旧材料放进每次请求不仅昂贵，也会让过时线索挤占注意力。Harness 可能触发上下文压缩（Compaction）：保留用户目标、项目约束、最近修改、失败原因与未完成事项，对较早历史进行取舍或概括，并把不再需要的材料移出当前视图。

压缩解决的是“模型这一刻装得下什么”，不是把过去变成永远正确的记忆。摘要是有损的；若它把“测试曾经失败，仍待确认”写成“测试已经处理”，下一轮就可能过早结束。因此，历史保存了什么、模型本次看见什么、以后能够重新取回什么，是三个相关但不同的问题。Token 管理也不只是省钱：它直接影响约束是否还可见、错误能否继续追踪，以及任务是否会在长链路中悄悄偏离原目标。

任务还可能在终端关闭、网络中断或用户主动暂停时停下。任务恢复（Resume）不能只是把旧对话重新显示出来。恢复材料可以告诉 Harness 上次讨论和执行到了哪里，却不能保证文件、分支、依赖或外部进程仍保持原样。稳妥的恢复会先核对当前工作区、关键修改、活动进程和必要测试，再决定继续、重做还是向用户询问。保存过去是连续性的条件，重新观察现在才是继续行动的依据。

另一种压力来自工作范围而非窗口大小。根 Agent 可以把“定位解析入口”或“独立检查回归测试”委派给子 Agent（Subagent），让局部调查在较小上下文中进行。但委派不是责任消失：父任务仍要控制交给子任务的材料与权限，处理取消、并发修改和结果汇聚，并检查子 Agent 的报告是否与共享工作区相符。压缩改变信息的表示，委派改变工作的拓扑；二者都要求主任务保住目标与最终验证权。

从用户视角看，这些机制最好不要把一个任务割裂成互不相认的片段。压缩之后仍应知道原始要求，恢复之后仍应知道哪些结果已经过时，子任务返回后仍应看得出结论来自调查还是实际修改。连续性不是保存越多越好，而是让系统在边界变化后仍能说明：当前目标是什么，现实已经发生了什么，下一步为何合理，以及哪些决定还需要用户参与。

## 完成不是模型说“完成了”

当候选修复形成后，任务进入最容易被一句自然语言掩盖的阶段：验证。Harness 需要重新查看关键修改，确认代码差异（diff）只覆盖预期范围，运行相关测试并保留命令结果，然后让模型解释错误原因、修改方式、验证范围和仍有的不确定性。只有这些可核对的结果彼此一致，模型关于“已经完成”的说法才有工程意义。

这里的“完成”因此是一项工程判断，而不是模型输出中的一个词。测试可能只覆盖局部分支，工作树可能混有任务开始前的修改，取消过的进程也可能留下产物。Harness 要根据最新观察判断是否达到用户要求，并在无法确认时明确留下未决问题。即使任务已交付，保存的会话也只记录过去；未来恢复时，外部世界仍要重新核对。

沿这次修复走到末尾，因果关系已经清楚：模型提出正确建议，并不等于修改已经落到正确工作区，也不等于副作用受到控制、失败得到反馈、测试足以支撑交付。缺少这些连接与控制，模型建议无法自然成为可信的软件工程结果。第一章将从这里接过问题，给出正式工作定义，并进一步区分模型、Agent 与 Harness。

这也改变了评估 Coding Agent 时应该提出的问题。一次修复成功，可能得益于模型找到了正确原因，也可能得益于 Harness 提供了合适的仓库视图、把失败测试及时送回，或阻止了越界修改；一次失败，同样可能发生在模型判断、上下文选择、工具接口、权限策略、执行环境或恢复环节。只比较最终回答会把这些原因揉成一个分数，而分析 Harness 则尝试把它们重新拆开。

解决这些工程问题，并不自动要求某一种内部结构。集中式程序可以在一条循环里完成大部分工作，平台式系统可以把会话、调度、权限和执行拆开，插件式系统还可以在运行时组合能力。为了在谈论不同实现时仍指向同一套问题，[统一参考架构](04_reference_architecture.md)把横向能力与纵向时间线翻译成稳定的结构边界：谁作决定，谁改变工作区，什么属于当前可见信息，什么属于保存状态，什么又是可交付结果。

## 用三种视角理解七个 Harness

本报告选择 [Aider](18_code_editing_git_and_workspace.md#aider以-git-基线组织编辑事务而不是通用工具总线)、[Codex](17_security_permissions_and_sandboxing.md#codex审批权限画像沙箱网络与凭据代理组成安全控制面)、[DeepSeek Harness](09_plugins_mcp_and_extensions.md#deepseek-harnesscordis-插件图让产品行为成为可组合生命周期)、[Gemini CLI](09_plugins_mcp_and_extensions.md#gemini-cliextension-不只是插件包而是受管理的贡献集合)、[Goose](20_interfaces_and_human_in_the_loop.md#goose以-mcp-extension-和-acp-把能力生态与客户端状态接在一起)、[OpenCode](20_interfaces_and_human_in_the_loop.md#opencodeserver-是权威状态边界客户端只是不同投影) 与 [Pi](16_subagents_and_orchestration.md#pi小内核不是缺功能而是把治理和编排变成-extension-责任) 作为七个 Coding Agent Harness 样本。它们面对相似的工程任务，却把控制中心放在不同位置：有的紧密围绕版本控制系统（Git）与编辑组织任务，有的以会话和工具调度组织运行，有的依靠插件装配能力，有的保持可编程的小内核。把它们放在一起，不是为了给产品排出名次，而是为了观察相同问题可以怎样分解，以及不同边界会带来什么工程与安全取舍。

本报告用三种互补视角建立共同坐标。横向视角把同一时刻的系统摊开，比较共同能力以及七个样本把循环、上下文、执行、扩展、连续性与控制放在哪里；[横向能力地图](02_horizontal_capability_map.md)适合回答“它们有什么共同底座，又在哪里分叉”。[纵向生命周期](03_vertical_lifecycle_walkthrough.md)沿一项任务从请求走到交付，关注能力何时出现、失败怎样回流、中断后如何继续。[统一参考架构](04_reference_architecture.md)把“能力在哪里”和“阶段何时发生”翻译成组件责任与状态边界。

个案视角则把分散在机制比较中的选择还原到每个系统的整体架构、历史约束与设计哲学。报告会在共同坐标之后进入核心机制、Coding 工作流与七个个案，再回到跨系统综合：机制章回答 Context、工具、扩展、会话、压缩、委派、安全、可观测性等问题如何单独成立又彼此连接；个案章解释这些机制为何以特定方式组合；综合部分再讨论可迁移的设计原则、整体取舍和开放问题。这样既能比较，又不必把每个系统压扁成同一种实现。

不同读者可以沿不同路线进入：

- **第一次接触 Harness 的读者**：按 `00 → 01 → 03 → 04 → 05 → 07 → 08 → 12` 建立从直觉、生命周期到核心机制的主线，再任选一个个案章并阅读第 30 章综合比较；横向地图、研究议程和与当前问题无关的个案可按需选读。
- **使用或评估 Coding Agent 的工程师**：按 `00 → 02` 先确认问题边界和横向坐标，再带着具体问题进入第 05–22 章、相关个案章与第 30 章；纵向生命周期和参考架构可在需要核对顺序或术语时按需回查。
- **Harness 或 Agent 平台开发者**：按 `01 → 04 → 05–22 → 23–30 → 31` 从工作定义与参考架构进入机制、个案、综合和设计原则；第 32 章研究议程与主题参考文献可按需进入。
- **安全研究者**：按 `01 → 04 → 07–10 → 12 → 16–17 → 19 → 22 → 30–32` 阅读，重点依次覆盖模型上下文、工具与扩展、提示词注入（Prompt Injection）到能力执行、权限与沙箱、持久化与恢复、Subagent、可观测性、配置与供应链，再进入综合与研究议题；界面细节和无关产品实现可按需选读。

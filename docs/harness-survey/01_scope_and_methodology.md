# 范围、术语与研究方法

**状态：提纲，待调查。** 本章为整份调研规定范围、术语和证据标准，而非对七个系统已经完成的功能断言。章节目标是让读者知道后文的比较回答什么、如何被源码和文献支持；读完后应能区分工程事实、默认配置与分析推断，并能沿证据入口复核。它接住报告索引提出的“自然语言如何变成可控行动”这一问题，随后把比较坐标交给[横向能力地图](02_horizontal_capability_map.md)、把任务过程交给[纵向生命周期](03_vertical_lifecycle_walkthrough.md)，并由[统一参考架构](04_reference_architecture.md)固定状态对象。

## 什么是 Agent Harness

本文将 **Agent Harness** 暂定为：围绕大语言模型（LLM）组织 Coding Agent 任务的运行时与交互边界；它接收用户目标，准备代码与文本上下文，驱动模型—工具—观察循环，并对工作区、权限、持久化、恢复和产物施加工程控制。这里的“Coding”限定为对已有仓库进行阅读、修改、执行测试、使用 Shell 或 Git 并解释结果的任务；不讨论多模态输入输出，也不把模型本身或单一 IDE 插件直接等同于 Harness。

这一工作定义首先服务于分析，而非声称七个项目采用同一架构。后续应分别调查 Aider、Codex、DeepSeek Harness、Gemini CLI、Goose、OpenCode、Pi 如何把用户请求转换为可调度的行动；若某系统只实现其中一部分，地图应显式保留缺口，而非以名称补全能力。术语的最小状态定义由[第四章](04_reference_architecture.md)先行给出，循环细节则移交给[第五章](05_harness_loop.md)。

**代码证据计划：** 从 `aider/aider/coders/base_coder.py`、`codex/codex-rs/code-mode-protocol/src/session.rs`、`deepseek-harness/packages/core/agent/`、`gemini-cli/packages/core/src/core/client.ts`、`goose/crates/goose/src/agents/state_machine/`、`opencode/packages/core/`、`pi/packages/agent/src/harness/session/session.ts` 继续追踪启动入口、状态对象、调用链、异常路径与测试；这些路径只是待调查入口，不是能力结论。

## 为什么选择这七个系统

样本固定为当前父仓库锁定 revision 的 Aider、Codex、DeepSeek Harness、Gemini CLI、Goose、OpenCode 与 Pi。选择原则不是给项目排位，而是覆盖面向代码仓库的不同实现取向：成熟的 Git 交互、Rust 或 TypeScript 运行时、可扩展工具生态、会话状态、终端与其他客户端入口等都可能构成可比较的设计变量，必须以后续源码调查确认其边界和实际默认值。

公平的样本描述应记录每个 submodule 的固定 commit、可读源码范围、许可与构建线索，而不从 README 的宣传语推出行为。若一个入口、测试或依赖在该 revision 缺失，应记录为“未证实”或“范围外”，不能以另一个版本、在线服务或名称相近的组件代替。第[23](23_codex.md)至[29](29_aider.md)章将解释各系统的组合理由，本章只给出共同的选择与版本纪律。

**图表计划：** 在本章或附录制作“样本与证据覆盖表”：行是七个固定 commit，列是启动入口、状态模型、工具执行、权限/错误路径、测试和文档。单元格使用证据状态而非勾选式功能宣称，并链接到后续个案章。

## 代码如何成为工程结论

工程结论应从固定 revision 的可执行路径开始：识别用户入口或 API，追踪到 session/loop、tool dispatch 和副作用，再查看取消、异常、持久化与测试如何约束它。README、示例和配置模板可以解释设计意图，却不能独自证明默认行为；同样，单个类型名或测试名也不等于完整调用链。每个可发表的比较命题应留下短的源文件定位、所处状态对象和对应测试或错误路径。

调查记录采用五个彼此不可替换的标签：**Documented** 是项目文档声明；**Implemented** 是当前源码存在实现；**Default** 是在固定版本、已声明前提下的默认设置；**Verified** 是按记录环境实际复现；**Inferred** 是从前四者推导的分析。尚未走完入口—调用链—异常/取消—测试的项目一律写“待沿此入口调查”，并在[第十九章](19_observability_evaluation_and_replay.md)补充可观测和回放证据。

**安全分析计划：** 每条工具或插件链同时标出模型输入、配置输入、工作区、凭据、网络、Shell、文件系统和 Git 的跨界点；调查时先问“谁可触发、谁审批、什么可变、何处留下审计痕迹”，再进入[第十七章](17_security_permissions_and_sandboxing.md)的权限和沙箱论证，避免把“有确认 UI”简化成安全结论。

## 论文如何进入学术解释

学术材料的作用是解释工程机制的概念谱系和设计取舍，例如 agentic software engineering、工具调用与人机协同、长期上下文与记忆、软件供应链与最小权限；它不能替代对七个 checkout 的实现调查。检索从问题开始而非从预设立场开始：每个机制建立关键词、候选原始论文/标准、反例和待回答的工程问题，再核验作者、题名、venue、年份与 DOI 或稳定 URL 后，才进入正式参考文献。

本组章节不会编造论文引文、生产观察或实验数字。待检索的学术问题包括：会话恢复应以何种状态一致性描述，工具权限如何连接到可追责的人类监督，以及上下文压缩如何影响任务连续性。它们将分别为[第十二章](12_session_persistence_and_resume.md)、[第十七章](17_security_permissions_and_sandboxing.md)和[第十三章](13_compaction_and_context_management.md)提供解释框架，而不预先替这些章节下结论。

## 如何进行公平比较

公平比较以同一任务语义、同一状态词汇、同一证据强度和同一版本边界为前提，而不是以相同的 UI、模型提供商或命令行语法为前提。贯穿案例是：用户要求 Agent 在已有仓库定位并修复配置解析错误，运行测试并解释修改。比较时将把它拆成输入解释、上下文准备、模型循环、工具副作用、审批与恢复等阶段；系统可在每个阶段采取不同做法，不能因为一阶段相似便推定全程相同。

横向矩阵只比较可观察的机制和取舍，例如控制位置、可扩展接口、默认人为控制和恢复对象；纵向叙事只说明该案例经过的状态转换。对于无法在同一环境运行的系统，应先给出静态调用链比较和限制，只有在版本、模型、配置、工作区和测量口径一致时才讨论运行证据或成本。该分工避免[第二章](02_horizontal_capability_map.md)与[第三章](03_vertical_lifecycle_walkthrough.md)重复，也为[第三十章](30_comparative_synthesis.md)保留综合判断。

## 证据状态与有效性边界

本报告的有效性受固定 revision、依赖可得性、外部模型服务、操作系统、认证状态和样本代表性约束。源码可以证明某路径被实现，却不能单独证明它在所有配置、所有 provider 或所有工作区均可用；一次运行可验证一个记录场景，也不能外推出吞吐、可靠性或安全性。报告将把这些限制随结论一起写出，并把版本、环境和命令保存到附录，而非把它们藏在脚注。

潜在威胁包括选择偏差（仅七个开源样本）、版本漂移（upstream 持续演进）、观察偏差（文档与实现不同步）、配置偏差（默认值受本地策略改变）和研究者推断偏差（将接口存在误读为语义保证）。缓解方式是固定 commit、双入口追踪、查看测试与错误路径、记录反证、区分上述五种状态标签，并让读者能从本章链接回到具体代码入口。下一章会在这些边界内建立横向地图，而非输出排名。

## 本章小结

本章把 Agent Harness 限定为 Coding Agent 的工程控制边界，并规定七个系统、五级证据语言、贯穿案例和安全/学术的调查纪律。接下来应先阅读[横向能力地图](02_horizontal_capability_map.md)了解比较轴，再阅读[纵向生命周期](03_vertical_lifecycle_walkthrough.md)观察同一案例如何穿过这些轴；两者共同依赖[统一参考架构](04_reference_architecture.md)的最小对象定义。

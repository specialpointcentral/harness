# 开放问题与研究议程

前置阅读可先看[七个 Agent Harness 的综合比较](30_comparative_synthesis.md#主要结论)与[设计原则中的冲突和取舍](31_design_principles.md#原则冲突与取舍)，但本章也可以独立进入。前文已经说明固定版本的七个系统怎样组织一次 Coding 任务。本章不再增加功能清单，而是追问这些工程机制还缺少哪些可检验定义、跨系统证据和公共研究基础。

仍以[“一句话请求先要落到正确的工作区”](00_index.md#一句话请求先要落到正确的工作区)为教学案例。用户要求 Agent 定位并修复配置解析错误、运行测试并解释修改。现有 Harness 可以完成这条路径中的许多局部步骤，却仍难以回答一组更严格的问题：如果[历史被压缩](13_compaction_and_context_management.md#自动和手动-compaction)、[任务被恢复](12_session_persistence_and_resume.md#resumereplaybranch-与-fork)、[工具来自动态插件](09_plugins_mcp_and_extensions.md#发现注册与生命周期)、[子智能体（Subagent）共享工作区](16_subagents_and_orchestration.md#共享-workspace竞争与结果汇聚)，系统怎样证明目标、[权限与外部副作用](31_design_principles.md#权限身份与外部副作用)和最终验证仍然一致？研究议程的对象正是这些跨层性质，而不是某个模型在一次演示中能否给出正确答案。

这里所说的开放问题，不等于工程上完全没有控制。相反，前文已经找到大量可用机制。问题在于这些机制通常以产品内状态、配置和测试存在，缺少可迁移的语义、可组合的保证与覆盖真实失效的评测。后续研究需要同时尊重实现差异与共同责任边界，把“能够运行”推进到“能够说明条件、复现证据并检验保证”。

## Harness 的形式化模型

[统一参考架构中的控制平面与执行平面](04_reference_architecture.md#总体结构控制平面决定执行平面行动)已经给出描述性框架，[会话（Session）、轮次（Turn）、工作单元（Item）、本轮上下文（Context）与任务产物（Artifact）](04_reference_architecture.md#八个核心对象一项任务由什么组成)也提供了跨系统词汇。它们足以解释七个系统，却还不是形式化模型（formal model）。例如，“工具结果进入下一轮”没有规定并行结果按什么顺序提交，“取消后停止”没有规定已经越过执行边界的动作处于何种状态，“恢复同一任务”也没有规定哪些配置、工具版本与工作区事实必须重新验证。

现有 Agent 架构综述常用推理、规划、工具调用、反思以及单 Agent 或多 Agent 拓扑整理系统。这些分类揭示了常见阶段与设计分歧，却没有为具体 Harness 给出可执行的状态迁移、失败终态或外部副作用语义 [@masterman2024agentarchitectures]。认知架构视角能够区分工作记忆、行动选择和长期记忆等功能 [@sumers2024coala]，AI Agents 与 Agentic AI 的分类也把持久记忆、动态任务分解和协作自治放到同一问题空间 [@sapkota2025agenticai]。这些工作提供概念坐标，但不能直接证明某个 Coding Harness 的运行循环（Loop）、Session 或权限路径满足同一性质。

一个可操作方向，是从前文已经验证的对象与边界出发，为 Harness 定义参数化操作语义（operational semantics）。状态需要同时表示当前任务身份、可见 Context、能力目录、待决与在途调用、已提交结果、权限作用域、资源所有权和外部世界摘要。迁移则区分模型提议、授权、执行开始、结果持久化、取消、压缩、派生与恢复。不同产品不必共享内部类型，只要能够把自己的事件映射到这组观察点，就可以检验“每个已执行调用最终得到成功、失败、取消或结果未知终态”等安全性与活性性质。

进一步的工作应建立参考模型与实现之间的符合性测试。研究者可以从真实事件轨迹生成状态迁移，检查调用配对、权限不扩张、分支隔离和终止条件，也可以对同一轨迹施加崩溃、乱序与版本变化，观察实现是否仍产生允许的终态。形式化的价值不在于把七个系统改造成一种架构，而在于让集中式循环、分层运行时、插件图和小内核能够用同一组可证伪问题比较。

## Tool-use 与 Prompt Injection

这里的工具使用（Tool-use）沿用[从模型意图到可执行能力的工具调用（Tool Call）链](08_tool_call_system.md#工具如何成为模型的行动空间)，提示词注入（Prompt Injection）则沿用[低信任内容进入能力执行的源到汇（source-to-sink）路径](17_security_permissions_and_sandboxing.md#prompt-injection-到能力执行)。现有工程已经把工具发现、参数授权、人工审批、沙箱与凭据隔离分层，也能在部分路径记录调用来源。然而，这些控制通常分别验证，尚不能说明一段污染内容经过检索、压缩、子 Agent、模型上下文协议工具（Model Context Protocol Tool，MCP Tool）与重试之后，端到端策略仍然成立。

间接提示词注入研究已经证明，攻击指令可以藏在网页、文档或工具结果中，再借助 Agent 的真实能力产生后果 [@greshake2023indirectpromptinjection]。AgentDojo、ToolEmu 与 ASB 等评测进一步说明，安全不能只统计模型是否拒绝恶意文本，还要同时观察正常任务效用、最终 Tool Call 与真实或模拟副作用 [@debenedetti2024agentdojo; @ruan2024toolemu; @zhang2025asb]。CaMeL 与 Progent 分别代表数据流隔离和面向工具调用的策略生成方向，但它们仍需要与动态工具目录、人工批准、Session 恢复和插件生命周期组合后再检验 [@debenedetti2025camel; @shi2025progent]。

下一步研究应把内容来源追踪与能力策略连接起来。每段外部数据需要携带来源、信任级别、允许用途和传播历史，模型产生的参数再标出依赖了哪些数据。策略执行点据此判断某个文件片段能否影响网络目标、某个工单字段能否进入命令解释器（Shell），或某个可检索记忆条目能否触发写操作。这个方向不要求模型完美解释因果，但要求 Harness 保留足够的来源追踪（provenance），使高副作用调用可以被拒绝、复核或事后审计。

评测也应覆盖攻击链的组合变化。一个基准案例需要同时改变恶意内容入口、工具集合、审批模式、执行隔离、历史压缩与恢复时点，并分别报告任务完成、攻击达成、人工负担和资源成本。Agent 评测综述已经把安全、鲁棒性与成本的联合评估列为明显缺口 [@yehudai2025agentevalsurvey]。若研究只固定模型而忽略 Harness 配置，或者只报告攻击文本是否被复述，就无法定位真正切断或放大风险的系统层。

## Memory 污染和 Compaction 保真

[可检索记忆（Memory）的写入、范围与更新](10_memory.md#写入检索更新与遗忘)和[上下文压缩（Compaction）的信息保真度](13_compaction_and_context_management.md#信息保真度与摘要漂移)已经形成两条独立工程链。来源、新鲜度、项目范围、摘要检查点和原始 Artifact 都能降低错误传播。不过，现有实现很少给出统一指标来回答：一条错误何时成为持久先验，经过多少次检索或摘要改写后影响了新任务，以及系统能否把污染精确回滚而不删除仍有效的经验。

长期 Memory 的风险不止是召回错误条目。AgentPoison 表明，对记忆或检索库的污染可以在未来查询触发行为偏移 [@chen2024agentpoison]；A-MEM 一类动态记忆系统又允许新条目建立链接并反向更新旧记忆，使适应能力与污染传播共享同一机制 [@xu2025amem]。Agentic RAG 综述因此把记忆管理、协调、效率与治理同时列为开放挑战 [@singh2025agenticrag]。另一方面，摘要研究表明，流畅压缩仍可能遗漏原文事实或新增不受支持的内容，压缩比本身不能代表忠实度 [@maynez2020faithfulness; @jiang2023llmlingua]。

研究可以先建立带类型的记忆声明。每条可复用内容不仅保存文本，还保存来源 Artifact、适用项目与版本、创建主体、置信状态、反例以及被哪些后续条目更新。写入、合并、降权和删除形成可审计演化，而不是覆盖式“最新文本”。当新测试或文件读取推翻旧结论时，系统能够找到受影响的派生 Memory 与摘要，而不是依靠另一次模型生成猜测传播范围。

Compaction 保真则需要面向任务不变量评测。测试集应构造包含禁止事项、未完成 Tool Call、取消结果、精确文件名、相互冲突证据和外置 locator 的长 Session，连续执行多轮压缩与恢复，再检查目标、状态与来源是否保持。可进一步用污染注入比较“原始历史未污染、摘要污染、Memory 污染、两者交叉污染”四类路径。真正有用的指标不是摘要与原文词面多相似，而是 Agent 能否在新现场中作出正确核验，并避免把旧推断当成当前事实。

## Token 效率与质量边界

[令牌（Token）账本与七系统质量边界](14_token_efficiency_and_cost_control.md#七系统指标与质量边界)已经说明，单次输入更短、缓存命中更多或父 Session 消耗更少，都不等于任务整体更高效。不同模型服务提供者（Provider）对缓存、推理与输出的计量口径不同，Subagent、摘要、蒸馏、重试和外置存储又会把成本移到主调用之外。现有工程能够分别观测许多桶，却缺少跨系统可复现的“每个可信成功任务”的资源定义。

FrugalGPT 把成本控制组织为提示适配、模型近似与级联，说明低成本模型和按难度升级可以减少部分请求费用 [@chen2024frugalgpt]。但 Harness 还要承担文件选择、工具结果（Tool Result）、权限等待、失败重做与最终验证，不能把问答任务上的价格收益直接外推。新近 Agent 评测综述同样指出，成本效率仍未与安全、鲁棒性和细粒度行为充分联合报告 [@yehudai2025agentevalsurvey]。因此，“更短”只有在目标、约束、验证和恢复能力没有下降时才构成效率改进。

研究方向之一是建立任务级资源剖面。每次运行应同时报告主模型与辅助模型调用、缓存读写、子树总账、工具与存储开销、等待时间、人工干预，以及最终测试、diff、约束遵循和风险结果。比较时固定任务、模型、权限与停止条件，并把预算耗尽、环境失败和错误完成分开。这样的记录允许观察多目标边界，而不必压成一个会掩盖质量退化的总分。

另一方向是把预算策略做成带反馈的控制器。系统根据任务进展、证据新鲜度、上下文压力和剩余验证工作动态选择检索、压缩、弱模型或 Subagent，而不是只按窗口比例触发。关键实验应对每种策略做因果消融，判断节省来自减少无关输入、减少失败轮次，还是把工作转移到不可见辅助路径。质量边界一旦被触发，控制器应选择重新读取、升级模型或交还用户，而不是继续压缩直到任务表面完成。

## Resume 与副作用一致性

[任务恢复（Resume）与外部副作用状态](12_session_persistence_and_resume.md#tool-call-和外部副作用的一致性)已经区分未启动、结果未知和结果已提交，[可靠性机制中的幂等性与补偿](21_reliability_and_resource_control.md#幂等性与外部副作用)也提供了查询、重试与人工确认路径。这些做法能够处理具体文件或 API，却没有形成跨 Tool 的统一契约。尤其当一个动作同时写文件、启动进程并调用远端服务时，Harness 很难知道哪些部分已经发生、哪些能够重复、哪些需要补偿。

回滚恢复研究早已区分内部状态恢复与外部输出一致性 [@elnozahy2002rollback]，持久函数则通过记录步骤结果、重放确定性控制逻辑和隔离外部活动来支持长时间工作流 [@burckhardt2021durablefunctions]。Agent Harness 与这些系统相似之处在于都要跨故障保存进度，差异在于 Tool 往往来自开放扩展，参数由模型生成，外部服务也未必提供事务、幂等键或状态查询。因此，不能只把 Session 的事件日志（Event Log）套上工作流术语就认为问题已经解决。

可操作的研究起点是副作用描述符（effect descriptor）。Tool 在 Schema 之外声明它可能读取或修改的资源类别、是否支持幂等键、怎样查询提交状态、是否提供补偿、结果未知时应采取什么策略。Harness 在执行前持久化调用身份与描述符，在执行后记录对端身份和可核验结果。恢复逻辑据此选择读回、查询、补偿、隔离重试或请求人工决定，而不是让语言模型仅凭旧对话判断。

实验方法应采用系统化崩溃注入。在调用参数形成、审批完成、请求发出、远端提交、结果接收与本地持久化之间分别中断进程，再检查重复副作用、遗漏结果、悬空资源和错误终态。对缺少幂等支持的真实服务，可以用可观测代理记录请求与提交顺序。研究目标不是承诺所有外部动作都能回滚，而是准确缩小不确定区间，并证明 Resume 不会把“不知道是否发生”悄悄改写成“可以重新执行”。

## Multi-agent 权限与责任

[多智能体（Multi-agent）的父子身份、共享工作区与责任边界](16_subagents_and_orchestration.md#token权限与责任)已经说明，独立 Context 不等于独立 Workspace，角色提示词（Prompt）也不等于强制权限。现有系统能够记录父级（Parent）、子级（Child）、任务或会话谱系，并以工具过滤、并发限制和父级复验减少风险。但当任务跨进程、跨主机或跨组织 Agent 时，谁能授予能力、谁承担错误决策、哪个执行环境执行了动作，仍没有共同语义。

多 Agent 研究通常关注通信、角色分工、协作拓扑和性能。AutoGen 展示了可对话 Agent 的组合方式 [@wu2023autogen]，相关综述进一步整理了多 Agent 架构与协调挑战 [@guo2024llmmultiagentsurvey]。MAST 对失败轨迹的分析则表明，规范违背、对齐不足和任务验证缺失会在多 Agent 系统中相互传播 [@cemri2025mast]。IoA 与 Agentic AI 分类又把异构发现、动态组队和协调失败推到开放环境中 [@chen2024internetofagents; @sapkota2025agenticai]。这些文献解释了协作为什么困难，却还没有给 Coding Harness 一套权限与责任的可执行契约。

研究应把每个 Agent 视为有身份的主体，而不是一段名字不同的 Prompt。委派消息需要声明任务、可见数据、能力上限、预算、截止条件、工作区范围和验收者；Child 只能收窄权限，扩张必须回到明确授权主体。每次 Tool Call 还要携带从用户到 Parent、Child、扩展（Extension）与执行器的来源链。这样，故障调查才能区分任务分解错误、局部执行错误、运行时隔离失败和父级验收遗漏。

责任研究还需要超越“记录是谁做的”。一个可审计系统应说明谁提出动作、谁授权、谁执行、谁验证、谁有能力取消或补偿，以及信息在交接时丢失了什么。基准可以故意制造冲突建议、失联 Child、共享文件竞争、恶意子任务和预算耗尽，检验权限是否静默扩大、父级是否依据 Artifact 而非自然语言投票验收。责任不是把失败简单归给某个 Agent，而是让控制决定与证据链足以支持修复和治理。

## MCP 和插件供应链

[模型上下文协议（Model Context Protocol，MCP）的能力交换与 Host 边界](09_plugins_mcp_and_extensions.md#mcp-transport-与双向能力)已经标准化部分发现、调用与传输，[插件（Plugin）、技能（Skill）与更新的来源治理](22_configuration_identity_and_supply_chain.md#pluginmcp-与-skill-来源)也覆盖版本、依赖、完整性与激活范围。尚未解决的问题是：协议互操作通常止于消息可解析，供应链控制通常止于制品可识别，两者都没有自动给出权限语义、行为兼容、责任归属或恢复一致性。

MCP 规范明确管理宿主（Host）、客户端（Client）与服务器（Server）之间的上下文与能力交换，而不管理完整 Agent Loop [@mcp20250618]。协议综述进一步区分面向上下文或工具的协议与面向 Agent 间通信的协议，并把安全、可扩展性、延迟、隐私和群体交互列为比较维度 [@yang2025agentprotocols]。IoA 提出的异构 Agent 集成、动态组队与对话流控制说明，开放协作需要的对象比工具模式定义（Tool Schema）更多 [@chen2024internetofagents]。这些研究原型和分类不能替代现行协议字段，却指出了互操作边界之外的缺口。

供应链方向需要把“谁发布了什么”与“运行时允许做什么”连接起来。签名与透明日志可以验证制品和发布身份，Sigstore 展示了使用短期证书与透明记录保护发布链的路径 [@newman2022sigstore]，但来源真实不等于代码无恶意。后续标准可以要求 Server、Plugin 和 Skill 携带可验证身份、精确版本、依赖摘要、贡献清单、所需文件与网络能力、数据保留声明和更新策略，再由 Host 根据本地政策决定是否安装、激活和逐次授权。

互操作测试也应从“能连上”推进到语义符合。测试套件需要覆盖版本协商、Schema 漂移、名称冲突、取消、超时、在途卸载、错误分类、反向请求、凭据（Credential）作用域和恢复后的工具代际。最小权限与完全仲裁仍是底线 [@saltzer1975protection]，但标准化可以让 Host 知道在哪些边界实施这些原则。研究成果应同时包括协议扩展、威胁模型、符合性测试与迁移策略，避免新字段只增加声明而没有可验证行为。

## 评测、真实数据与标准化

[Harness 评测（Harness Eval）与模型评测的边界](19_observability_evaluation_and_replay.md#harness-eval-与模型-eval)已经要求固定仓库、模型、工具、权限、预算与验证器，并保存差异（diff）、测试、轨迹和资源。现有项目也有行为测试、容器任务、编辑基准或[会话回放（Session Replay）](19_observability_evaluation_and_replay.md#replay-与确定性边界)。问题在于这些入口服务于不同产品目标，任务格式、事件语义、失败分类和成本口径不一致，难以支持跨版本复现，更缺少经授权、脱敏且保留长尾失败的真实使用数据。

SWE-bench 用真实仓库问题和测试结果建立可执行软件任务 [@jimenez2024swebench]，SWE-agent 说明智能体与计算机之间的接口设计会显著改变同一模型的行为 [@yang2024sweagent]。AgentBench 则通过多个交互环境评估长期推理、决策与指令遵循，提示单一环境总分会掩盖失败结构 [@liu2024agentbench]。这些基准分别覆盖仓库结果、接口与通用交互，却都不能单独回答 Resume、副作用、供应链和多 Agent 责任问题。

下一代任务包应把初始环境、Harness 代码提交（commit）、模型与 Provider、工具及版本、权限和网络、预算、预期 Artifact、验证器（verifier）、允许副作用和失败分类放在一起。输出同时报告功能结果、安全结果、资源消耗、人工介入与可恢复性。模型评委可以补充解释开放式质量，但其位置、冗长与自我增强偏差意味着评分依据必须保留，且不能替代执行式验证 [@zheng2023llmjudge]。标准化的目标是让结果可解释和可重跑，不是制造跨场景的单一排行榜。

真实数据需要单独的数据治理路线。线上 Session 能提供长尾工具错误、用户纠正、版本漂移和部分完成状态，却也包含源码、凭据、组织身份与不可复现服务。研究者应取得明确授权，将轨迹转换为最小任务、固定快照和受控 verifier，保留从原事件到脱敏案例的转换 provenance，并允许数据主体撤回。持续更新的基准可以缓解训练污染与环境陈旧，但不能替代真实使用分布 [@yehudai2025agentevalsurvey]。

标准化还应覆盖观测事件的最小语义，例如 Session、Turn、模型请求、Tool Call、审批、执行结果、取消、压缩和派生关系。公共 Schema 不必强迫内部实现一致，只需让评测器可靠识别身份、终态、资源和来源。这样，研究才能把一次成功分解为正确定位、受控执行、有效验证和可恢复完成，也能把失败归入模型、Harness、环境或政策，而不是全部压成“通过”与“失败”。

## 未来 Corpus 扩展

当前七个固定版本构成的是研究语料库（Corpus）的一个架构切面，[版本清单](91_version_manifest.md#清单使用说明)保证结论能够回到具体快照，[综合比较的架构谱系](30_comparative_synthesis.md#架构类型与谱系)则说明样本已经覆盖集中编辑、分层 Session 运行时、组合式插件图和可编程小内核。它仍不是 Agent Harness 的全集。新的产品形态、协议入口、远端执行、企业策略与专用工作流会不断改变控制中心，也可能暴露本报告尚未观察到的状态与信任边界。

扩展 Corpus 时应按研究问题采样，而不是按项目热度填名单。Agent 评测综述观察到基准正在转向更真实、更困难且持续更新的任务，同时仍缺少成本、安全与细粒度评测 [@yehudai2025agentevalsurvey]；协议综述对上下文协议与 Agent 间协议的区分，也说明样本选择会直接决定研究能观察到哪类互操作问题 [@yang2025agentprotocols]。因此，若要研究 Resume，应优先加入具有长期作业（Job）、远端副作用或多客户端接管的系统；若要研究供应链，应加入有市场、签名更新或托管策略的实现；若要研究 Multi-agent，则需要跨进程、跨机器和异构协议样本。封闭系统只有在能够获得稳定公开协议、可重复黑盒实验和明确版本时才适合进入对照，不能用产品文案补齐不可观察的内部机制。

Corpus 还应成为纵向基础设施。每次更新保存源码或协议快照、构建环境、配置、评测适配器、证据定位与结论变化，并把“上游新增能力”“默认值改变”“旧证据失效”和“研究问题重新定义”分开。对快速演进的 MCP、模型 API 与插件生态，同一项目的多个时间点可能比不断增加项目数量更有研究价值，因为它能揭示迁移、兼容和政策变化怎样影响既有 Session 与评测结论。

最终，未来 Corpus 应服务于前八项议程：形式化模型提供共同观察点，安全研究提供攻击链，Memory 与 Compaction 研究提供长期状态案例，Token 研究提供完整资源账本，Resume 研究提供崩溃轨迹，多 Agent 研究提供责任谱系，协议研究提供供应链身份，评测研究提供可重复任务包。只有让新增样本改变或检验这些问题，扩展才会增加知识，而不是扩大目录。开放问题不会因某个项目新增一个功能而结束；它们要在明确条件、可复现证据和可证伪保证之间逐步收敛。需要沿主题继续追索文献时，可进入[参考文献阅读入口](93_references.md#主题阅读顺序与正文对应关系)。
